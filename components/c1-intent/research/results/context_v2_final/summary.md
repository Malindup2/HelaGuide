## Decision rules

- p-values: exact McNemar on per-turn correctness (majority over seeds), Holm-corrected within each model × test set × metric family. CIs: 95% cluster bootstrap over sessions (1000 resamples).
- **H1** supported when every context strategy beats current_only on JGA (CI > 0 and Holm p < 0.05); not supported when every one is significantly worse; otherwise inconclusive.
- **H2** is a non-inferiority claim. **Primary decision:** the 95% bootstrap CI of JGA(S) − JGA(full_history), resampling sessions and, independently for each strategy, seeds (1000 resamples). Supported when S uses fewer tokens and the CI lower bound is above −0.05; not supported when S is not cheaper or the whole CI is below −0.05; otherwise inconclusive. Margin set with `--ni-margin`; a sensitivity table repeats the verdicts at 0.03. **Secondary:** exact McNemar on majority-vote correctness (Holm). When the two disagree the row is marked *conflicting*, with the reason.
- **H3** statistic: the difference in drop from full_history between high-CMI and monolingual turns. Short follow-up answers are mostly monolingual and first requests mostly code-mixed, so turn position is confounded with code-mixing, and the statistic is computed within position strata (test set × first / follow-up turn) and combined weighted by the high-CMI + monolingual turns in each. The **headline is a permutation test**: CMI bucket labels are shuffled within each stratum (5000 permutations, fixed seed), keeping sessions and per-turn correctness fixed; two-sided p, Holm across the 6 strategies per model × test set. Supported when at least one strategy has Holm p < 0.05 with ≥ 30 turns in both buckets; otherwise inconclusive. It is the headline because it is the method whose false-positive rate on null data is closest to 5% (`h3_calibration.py`). The bootstrap versions (stratified, all turns, follow-up only; supported when an unadjusted 95% CI excludes 0) are secondary and over-reject on null data; their calibration rates are shown with them.
- Strategies marked *oracle (gold tags at test time) — upper bound* read the gold language/entity tags of earlier turns, which a deployed system does not have; their results are upper bounds.
- An overall verdict mixes per-strategy verdicts: all supported → supported, all not supported → not supported, else inconclusive (mixed).

## Scale claim: cheap and fast enough on CPU

Budgets (`bench_cpu.py`): p95 ≤ 500 ms per turn at 1 CPU thread and ≤ 2048 MB per worker. A chat reply should come in under about 1 s in total, and C1 may take at most half of that because C2–C4 also run on every turn.

**not supported: deployed engine p95 412.0 ms per turn at 1 thread (budget 500 ms), peak memory 3315.4 MB per worker (budget 2048 MB); 4-core ESTIMATE 14.2 turns/s**

The latency part of this verdict uses the 1-thread timing, which is unreliable on this machine (caveat below); the measured 4-thread p95 of the deployed engine is 152.8 ms. Memory alone decides the verdict.

### Full-pipeline cost (deployed engine, end to end)

The deployed engine (`C1Engine` + `Session`, window_3, rules + XLM-R NER fallback) runs, per turn: word-level language ID, the intent model twice, XLM-R NER, the state tracker and the intent policy.

**Why two intent calls per turn:** the first reads the window_3 context and decides the conversation's request; the second, from the second turn on, reads the current message alone, so that a switch to another service or a complaint in the middle of a conversation is not hidden by the earlier turns (Observation 13: window_3 history turned a mid-conversation complaint into `passport_new`). The first turn needs one call.

**Measured, 4 threads (primary latency figure):**

|---|---|---|---|---|---|---|---|---|---|

1 thread. The 4-core numbers are an **ESTIMATE** (4 workers × 1 thread, linear scaling assumed), not a measurement; they are based on the 1-thread timings, so they are approximate.

| c1_engine | window_3 (deployed, full pipeline) | 1 | 275.3 | 412.0 | 3.55 | 14.2 | 3315.4 | 30.1 | 220.8 |

**Why it misses the budget:**
- memory: peak 3315.4 MB per worker against a budget of 2048 MB, because the engine loads three separate fp32 XLM-R models (language ID, NER, intent), each with its own copy of the encoder.
- Latency is within budget (p95 412.0 ms at 1 thread, 152.8 ms at 4 threads), so it is not a reason.

**Fixes (future work):**
- memory: one shared XLM-R encoder with three heads (language ID, NER, intent), so one copy of the weights; int8 quantisation or fp16 weights;
- efficiency: the four XLM-R forward passes per turn (language ID, two intent calls, NER) could become one with the shared encoder; ONNX Runtime or int8 for CPU inference; one intent call per turn (for example the current-message prediction only when the policy needs it).

## Caveats

- keyword_summary — oracle (gold tags at test time) — upper bound and structured_state — oracle (gold tags at test time) — upper bound: they read gold language/entity tags; summary reads only the text.
- Sessions are stitched from 2–4 short dialogues; gold slot states restart with each dialogue, so the tracker is reset there and JGA measures within-dialogue slot tracking with the strategy's intent.
- Synthetic language tags (for CMI) are LLM-written (897 turns) or hand-checked (80), not fully gold.
- Fresh is small (50 turns): most of its CMI buckets are under 30 turns.
- Latency in the predictions was measured on the notebook's device; the CPU numbers come from bench_cpu.py.
